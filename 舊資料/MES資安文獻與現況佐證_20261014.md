## 一、結論與查核範圍

目前已有部分可對照官方安全指引的措施，以及歷史源碼、測試與事故處置證據。這些足以說明安全控制的設計方向，尚不足以認定現行 MES 全面安全、已通過資安認證或符合某一 ASVS 等級。

本資料整理承接 2026/10/14 的官方文件查閱與本機唯讀查核。沒有連入正式伺服器執行新的資安測試，沒有修改 3443／3445、帳號、Cloudflare 或防火牆，也沒有進行滲透測試。使用者說明目前使用 3443 與 3445，3444 已停用；兩個環境仍須分別盤點，不能因埠號不同便推論隔離或備援成立。

本文件區分四類證據：

| 證據類型 | 能說明什麼 | 不能直接證明什麼 |

## 三、OWASP ASVS 5.0.0：用來建立可查驗的清單

### 文件資訊

- 發布單位：OWASP Foundation。
- 文件：Application Security Verification Standard，版本 5.0.0，2025。
- [官方專案頁](https://owasp.org/projects/asvs)。
- [固定 v5.0.0 版本文件目錄](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0)。
- [官方存放庫 PDF](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/OWASP_Application_Security_Verification_Standard_5.0.0_en.pdf)。

ASVS 提供 Web 應用技術控制的驗證要求，可用來檢查登入、授權、工作階段、輸入處理等範圍。正式研究引用條款時應同時保留版本與條款編號，避免不同版本編號混用。[R1]

### 本案判斷

留存程式有相關控制，是建立測試清單的起點。現行映像是否與留存程式一致、各控制是否涵蓋全部入口，仍需查證。不能把「使用 ASVS 當參考」寫成「通過 ASVS 認證」。

建議記錄欄位：條款版本與編號、適用範圍、測試環境與映像、測試日期、預期結果、實際結果、證據位置、未符合項目及改善狀態。此為後續方法，尚未完成逐條測試。

## 四、OWASP 授權指引：不能只靠隱藏畫面按鈕

OWASP 建議最小權限、預設拒絕，並在每次請求檢查授權；前端限制只能改善操作體驗，不能取代後端控制。對特定資源的存取也要檢查，知道單據編號不代表有權讀取該單據。[R2]

### 本次找到的內部佐證

9/23 API 留存源碼（內部佐證，未隨本次公開）約第 311–330 行包含：

- 缺少登入憑證時回傳 401。
- 查詢帳號是否啟用、核准及在有效期間內。
- 比對 session_version，不符時拒絕已撤銷的工作階段。
- 讀取權限不符時回傳 403。
- 區分過期與無效的登入憑證。

這是歷史源碼證據，不是今日正式部署全路由測試。

8/26 作廢權限測試紀錄（內部佐證，未隨本次公開）另記載：入庫人員僅能作廢本人建立資料、已存在下游紀錄時阻擋、使用交易鎖及軟作廢並記錄 Audit Log。該文件屬當時 3444 測試版本，不可冒充現行 3443 驗收。

### 後續測試案例

| 問題 | 預期驗證 |
| --- | --- |
| 未登入能否讀取入庫明細？ | 未授權請求不得取得敏感資料 |
| 查詢角色能否直接呼叫修改 API？ | 即使自行送出請求仍應拒絕 |
| A 廠帳號改成 B 廠單據 ID？ | 按核准的資料範圍拒絕越權，先確認業務是否授權跨廠共查 |
| 附件／PDF 能否繞過頁面權限？ | 檔案端點同樣遵守資料範圍 |
| 停用帳號或調整權限後舊憑證還有效嗎？ | 依設計撤銷，不僅要求重新整理畫面 |

上述是待測規劃，應先在獨立授權測試環境使用測試帳號與資料，不對正式作業擅自做修改測試。

## 五、Cloudflare：Tunnel 與 Access 的職責不同

Tunnel 由 cloudflared 主動對外建立通道，建立後請求與回應可雙向傳輸。配合來源端防火牆政策，可限制直接進入來源主機的路徑。這不代表所有入站埠已在本案關閉，也不等於公開 Web 應用不會受到惡意請求。[R3]

Cloudflare 官方建議另外建立 Access 應用及政策；若沒有 Access 應用，發布的應用仍可供網際網路使用者連入。應用本身仍可有 MES 登入保護，但不能宣稱已有額外的 Access 身分閘道。[R4]

### 目前能說與不能說

| 可以依紀錄說明 | 尚不能宣稱 |
| --- | --- |
| 建置紀錄使用 HTTPS 與 Tunnel 對外提供服務 | 因為有 Tunnel，所以任何人都不能攻擊應用 |
| MES 有自己的帳號與權限設計 | 已啟用 Access、多因素驗證及全部 WAF 規則 |
| 10/5 外網 TLS 憑證驗證曾通過 | 所有內外網路徑與來源憑證今天皆已嚴格驗證 |
| 有網域作為入口 | 網域名稱本身是防護或安全認證 |

需取得去除機密的現行證據：網域／通道路由、來源服務位置、發布埠與防火牆、來源端憑證驗證、Access 政策、管理帳號 MFA、WAF 適用規則。不同功能須個別確認，不能從一張 Tunnel healthy 畫面推論全部成立。

論文公開版可用 mes.example.com 取代真實入口；移除金鑰、Token、連線密碼與完整帳號清單。此公開文件不包含上述機密；內部來源僅列名稱，不附原始檔。

## 六、NIST SP 800-82 Rev.3：生產不中斷與可復原

### 文件資訊

- Stouffer, K., et al. (2023). Guide to Operational Technology (OT) Security. NIST SP 800-82 Rev.3。
- [官方出版頁](https://csrc.nist.gov/pubs/sp/800/82/r3/final)。
- [DOI](https://doi.org/10.6028/NIST.SP.800-82r3)。
- [官方完整 PDF](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-82r3.pdf)。

可引用第 6.2.4.3 節的備份與還原相關建議，以及附錄 E.3.1 Backup Storage。文件建議另存備份、測試還原程序、保護備份存取，並按風險規劃備份頻率、保存位置與期限。[R5]

查閱時官方另列 Rev.4 初始公開草案，本整理仍以 Rev.3 正式版為依據，不將草案寫成已發布的正式替代版本。

### 適用邊界

本案為生產管理 Web 系統。引用 NIST 是借用工業場域可用性、風險與復原原則，不代表已完成工廠全部 OT／PLC 防護，也不代表取得 NIST 認證。

### 已有事故證據

10/5 正式站事故紀錄（內部佐證，未隨本次公開）記載：

- Docker／WSL 執行環境中斷後，容器內服務恢復，但主機入口連線未正常恢復。
- 經使用者授權，僅重啟正式連線代理後恢復。
- 內外網首頁與 API 經多輪檢查回應正常。
- 外網 TLS 驗證通過，未登入 auth/me 回傳 401。
- 沒有以資料庫還原處理此事故。

該紀錄支持「有事故處置與恢復驗證」。WSL 最初退出原因未完全查明，且代理恢復不等於主機全毀後的災難復原演練。

### 還需要哪些復原證據？

1. 備份是否包含資料庫、附件、部署設定與必要版本資訊。
2. 備份副本是否位於不會與正式主機同時損壞的位置，並有存取限制。
3. 在獨立空白環境實際還原，核對帳號、資料、附件與關鍵查詢。
4. 記錄演練實際恢復時間及可恢復資料截止時間。
5. 定義業務可接受的恢復時間目標 RTO 與資料損失時間目標 RPO，再將實測與目標比較。

目前不能把 3445 存在、歷史快照同步或 GitHub 文件交接，直接等同自動備援或完整備份。

## 七、12 小時登入期限應如何解釋？

登入絕對效期、閒置逾時、登出失效與憑證撤銷是不同控制。OWASP 工作階段管理指引可作為檢查依據，但沒有因本案採用 12 小時便自動安全的結論。[R6]

可表述為：「已有登入期限與撤銷設計，還需依現場角色、共用裝置及離席風險，驗證工作階段的完整生命週期。」

應檢查：操作員離席時的平板狀態、職代是否使用本人帳號、登出後舊憑證、改密碼或停用後的舊工作階段，以及是否允許安全地換帳號。12 小時提醒畫面的外觀修正，也不等於後端期限機制完成安全測試。

不使用「百分之百安全」「不會被入侵」「Cloudflare 保證安全」「已通過 ASVS／NIST 認證」等未經證實的說法。
