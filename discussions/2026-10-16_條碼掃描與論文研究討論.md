# 2026/10/16｜條碼掃描、AppSheet 比較與論文研究討論

> 討論日期：2026/10/16（臺灣時間）。公開研究紀錄，承接 [10/15 的量化方法討論](2026-10-15_1027討論紀錄.md)。
> 本文區分使用者回饋、先前唯讀查核、官方資料及待驗證方案；不是部署紀錄，也不是已完成的改善成效報告。不公開內網位址、帳號、客戶、工令、原始條碼及原始營運日誌。

## 一、目前決策與研究主軸

H 公司 MES 由先前 AppSheet 作業方式轉換而來。使用者回饋：先前採用 AppSheet「System default」掃描器，一維條碼操作感受快速且精準；目前 MES 的一維條碼比 QR Code 慢。這是重要的現場比較線索，但尚未做控制條件一致的計時與正確率比較。

論文主軸仍是：以酸洗廠入庫為資訊串接起點，改善物料資訊取得、跨角色最新狀態一致性及人工協調負擔。不是預設紙本資料錯誤，也不是以 RAG 或自動攻防為主軸。

掃碼效能屬於資訊輸入端的可用性條件；不能把「掃碼變快」直接等同「跨廠同步改善」或「公司利潤增加」。

本次僅研究、文件化與 GitHub 存參；不修改、重啟或部署正式 MES。以下改善均待另行確認測試環境與實作範圍。

## 二、量化表單能否成為論文依據？

可以成為蒐集實證的工具，但完成表單不等於證明有效。正式結論須來自一致程序、真實樣本、合理比較及可追溯分析。

| 測量面向 | 要測什麼 | 不能混淆的事情 |
| --- | --- | --- |
| 資訊取得時間 | 生管提出問題，到取得可核對的入庫、入洗或出貨答案 | 不等於事件發生到所有人知道的同步延遲 |
| 最新狀態一致性 | 四角色對同一時間基準、同一任務的件數與急件資訊是否一致 | 四人不是四個獨立事件；一致也不保證共同答案正確 |
| 人工聯繫負擔 | 每件問題聯繫次數、參與人員與投入時間 | 主觀方便性問卷不能取代客觀計時 |

正式收集前須先試填，固定起訖點、超時規則及正確答案依據。若現在重演紙本流程，應稱「紙本流程重演比較」，不可寫成過去已實測的建置前數據。應控制任務難度、操作者及環境，交錯測試順序，避免記得答案使第二次比較變快。

保留未完成、錯誤、無回覆及超時案例；呈現完成率、時間中位數與分布。樣本數、配對或分群方式及統計方法須依試測與老師討論確定，不能先挑檢定再湊資料。正確答案須由核對過的單據、實物與紀錄判定，不直接認定 MES 畫面永遠正確。

可能結果是查詢時間縮短、一致性提高或聯繫減少，也可能部分任務沒有改善。例如急件仍需要主動通知，不能僅靠可查詢畫面。這些都可以形成研究發現。若要談職代接手效益，需另設接手任務；若要談利潤，需另有成本與財務資料。

已有五張正式空白表及示範填寫檔；示範資料不得進入統計。本次沒有新增正式觀測成果。

## 三、單台 iPad Safari 相機問題

使用者回報只有一台 iPad Safari 出現相機被封鎖提示。先前唯讀查核顯示該訊息對應瀏覽器的 NotAllowedError／PermissionDeniedError 分支，不能僅依訊息就斷言是使用者拒絕權限，更不能說是伺服器主動關閉相機。

當時服務仍有正常回應，沒有取得與該次相機故障相對應的伺服器重啟證據。相機錯誤主要留在瀏覽器端，伺服器紀錄不足以還原裝置狀態。

仍待確認：iPadOS 版本、網站相機權限、首次開啟或鎖屏／切換頁面後才發生、是否同時開啟多個掃碼頁。先前程式查核未看到完整的背景切換與串流中斷恢復流程，屬待改善方向，不是已證實根因。

WebKit 說明相機串流可能有靜音與恢復狀態；此資料只能支持檢查生命週期，不能證明本次故障原因。[WebKit：WebRTC](https://webkit.org/blog/7763/a-closer-look-into-webrtc/)

## 四、既有 MES 掃碼機制與慢速疑點

以下整理本日稍早唯讀程式與日誌查核，不代表再次量測或持續監控。

### 4.1 三個作業共用掃碼元件

入庫、自主檢查與出貨均使用共用 LiveQrScanner。既有解碼器為 ZXing JavaScript，啟用 QR Code、Code 128、Code 39、Code 93，以及較積極的辨識與反色嘗試。影像請求約為 1280×720，實際影像須由裝置回報確認。

嘗試／成功後的排程間隔設定約為 100／120 毫秒，這不是端到端掃碼時間保證，尚有影像處理、解碼與後續等待。

### 4.2 已找到的程式路徑

```text
開啟掃碼 → 登入狀態確認 → 啟動相機
每次辨識候選值 → 等待登入狀態確認 → 計入辨識確認 → 接受字串 → 查詢資料
```

QR 候選值一次即可接受；一維條碼另有字串規則與兩次一致確認，確認間隔至少約 80 毫秒，若距上次超過約 1.5 秒則重新計數。網路檢查在確認計數前，因此網路等待可能拉長兩次確認間隔；等待中其他候選結果被略過。

這是可解釋延遲的程式結構，但尚未用問題 iPad 的逐段時間戳證明它就是主要瓶頸。不可把合理推論寫成已完成因果驗證。

### 4.3 日誌的限制

當時抽取最近兩小時、最多 12,000 行的代理日誌樣本中，登入檢查 2,474 筆，中位數約 13 毫秒、P95 約 20 毫秒、最大約 173 毫秒；自主檢查條碼查詢 91 筆，中位數約 34 毫秒、P95 約 46 毫秒、最大約 59 毫秒。另有全部自主紀錄列表約 8.5 秒的單筆慢請求。

這些只是有限樣本的伺服器／代理耗時，不含平板相機、對焦、解碼、Wi-Fi、外部往返及畫面更新。不能據此說平板不慢，也不能將列表慢請求直接當作掃碼慢的原因。

## 五、為什麼支援很多格式仍能精準解碼？

### 5.1 不是 OCR 辨識下方文字

掃碼器主要將線條／方格圖案轉回編碼內容，並非看標籤下方的字再猜文字。以 ZXing 開源實作為例，各格式有特定圖案與解碼規則；Code 128 還檢查加權總和的模 103 檢查碼，不符合即拒絕。[Code128Reader 原始碼](https://github.com/zxing-js/library/blob/master/src/core/oned/Code128Reader.ts)

Code 93 有檢查碼處理；Code 39 的檢查碼可選，不能假定每張現場標籤都有，也不能一律強制啟用，否則合法標籤可能掃不到。[Code93Reader](https://github.com/zxing-js/library/blob/master/src/core/oned/Code93Reader.ts)、[Code39Reader](https://github.com/zxing-js/library/blob/master/src/core/oned/Code39Reader.ts)

檢查碼降低錯誤風險，不保證絕不誤讀；掃到正確字串也不代表串到正確入庫批次，仍須保留業務狀態檢查。

### 5.2 支援多種格式，不等於同時盲猜所有文字

ZXing 的一維多格式讀取器會按啟用的讀取器嘗試，成功即回傳，不需等所有格式都成功。這說明多格式可以有效率，但不是 AppSheet 內部演算法的證明。[MultiFormatOneDReader](https://github.com/zxing-js/library/blob/master/src/core/oned/MultiFormatOneDReader.ts)

### 5.3 一維碼與 QR 定位難度不同

Apple 舊版技術備忘錄指出，二維碼有容易尋找的定位圖案；一維碼則依掃描線與區域等機制偵測。可用來解釋為何方向、畫面位置與完整線條重要，但這是 AVFoundation 的特定文件，不可直接當成 Safari、ZXing 或目前 AppSheet 的內部設計。[Apple TN2325](https://developer.apple.com/library/archive/technotes/tn2325/_index.html)

### 5.4 AppSheet 目前可證實及不可證實的部分

官方提供 System default 與另需授權的 Scandit；內建支援多種一維／二維碼。官方相機掃描運行於行動 App，不支援網頁瀏覽器及編輯器模擬器；解碼值填入欄位。[AppSheet 官方掃碼說明](https://support.google.com/appsheet/answer/10106618?hl=en)

所查官方文件沒有交代 System default 的確切解碼引擎、逐幀確認數、對焦策略或延遲基準。因此不能宣稱 AppSheet 一定採 ML Kit／AVFoundation、只確認一幀，或完全沒有登入等待。使用者回饋可作為比較需求，不是演算法證據。

## 六、對 MES 有幫助的技術資料與用途

本次為針對性官方文件與原始碼查找，不宣稱窮盡所有文獻；以下多屬工程依據，並非每項皆為同儕審查論文。查閱日期：2026/10/16。連結至主分支的程式日後可能改變，正式實驗須固定套件版本與提交碼。

| 資料 | 可以支持什麼 | 對 MES 的用途與限制 |
| --- | --- | --- |
| [AppSheet 掃碼說明](https://support.google.com/appsheet/answer/10106618?hl=en) | 支援格式、行動 App 與欄位輸入行為 | 建立舊系統操作基準；不能推定內部引擎 |
| [Google ML Kit iOS 掃碼指南](https://developers.google.com/ml-kit/vision/barcode-scanning/ios) | 足夠像素、清晰對焦、限定格式及影像處理建議 | 作影像品質與效能設計參考；不是可直接貼入 Safari 的套件 |
| [Apple TN2325](https://developer.apple.com/library/archive/technotes/tn2325/_index.html) | 一維／二維定位及掃描區域差異 | 研究中心掃描區與方向；是歷史技術說明，不保證現行效能 |
| [Apple rectOfInterest](https://developer.apple.com/documentation/avfoundation/avcapturemetadataoutput/rectofinterest) | 限制搜尋區域的原生 API | 支持 ROI 概念；網頁需要自己的影像裁切實作 |
| [ZXing BrowserCodeReader](https://github.com/zxing-js/browser/blob/master/src/readers/BrowserCodeReader.ts) | 嘗試間隔與掃描迴圈 | 核對排程與解碼耗時，勿把設定間隔當總耗時 |
| [ZXing 多格式讀取器](https://github.com/zxing-js/library/blob/master/src/core/oned/MultiFormatOneDReader.ts) | 讀取器選擇及成功回傳 | 檢查是否啟用多餘格式；現場碼制未盤點前不刪格式 |
| [ZXing Code 128](https://github.com/zxing-js/library/blob/master/src/core/oned/Code128Reader.ts)、[Code 39](https://github.com/zxing-js/library/blob/master/src/core/oned/Code39Reader.ts)、[Code 93](https://github.com/zxing-js/library/blob/master/src/core/oned/Code93Reader.ts) | 解碼、檢查碼與拒絕機制 | 依真實標籤設計正確性測試，不能取消保護換速度 |
| [ZXing-WASM 專案](https://github.com/Sec-ant/zxing-wasm) | ZXing-C++ 可透過 WebAssembly 用於網頁 | 第二階段引擎候選；須測 iPad 相容性、載入時間與記憶體，不保證比現版快 |
| [WebKit WebRTC](https://webkit.org/blog/7763/a-closer-look-into-webrtc/) | 相機串流狀態與生命週期 | 區分權限、中斷與解碼失敗，不直接推定裝置根因 |

ML Kit 建議最小有效條碼單元具有足夠像素，通常至少約 2 像素；影像模糊會影響辨識。這是該引擎的指引，不是所有條碼絕對門檻。對 MES 的啟示是應測條碼實際占畫面的大小，而非只追求更高解析度。[ML Kit iOS 指南](https://developers.google.com/ml-kit/vision/barcode-scanning/ios)

## 七、建議修正順序（尚未實作）

1. **先分段量測。** 分開記錄相機啟動、第一個正確候選值、接受值、查詢完成及畫面呈現時間，確認慢在哪一段。
2. **調整確認流程。** 候選方案為本機連續解碼、兩個不同影格同值確認，再驗證登入並查詢／提交；避免每個候選值都把網路等待插入確認計數。保留伺服器授權及出庫／重複紀錄等檢查，不以跳過資安檢查換速度。
3. **優化影像輸入。** 中央 ROI 必須容納完整條碼與兩側留白，並有擴大或全畫面備援；測方向、對焦與不同解析度。螢幕上的框不等於解碼器真的只讀框內。
4. **盤點真實碼制。** 既有四種格式不代表都常用；先記錄格式分布。未知標籤保留回退，不憑感覺只留 Code 128。
5. **再比較引擎。** 現有 ZXing 與 WASM 候選以相同影像及即時相機分別測試；原生 App 方案涉及額外部署維運，不先決定。
6. **三個作業回歸。** 入庫、自主檢查與出貨共用元件，須驗證合法、已出庫、重複、查無資料與登入逾期等情境；不能只測一處就認定全部正常。

## 八、掃碼改善的驗證方案

| 指標 | 記錄方式 |
| --- | --- |
| 相機啟動時間 | 點開掃碼到有效預覽，與辨識時間分開 |
| 正確辨識耗時 | 標籤完整進入指定區域到接受完整正確字串 |
| 查詢耗時 | 接受字串到正確作業資料顯示 |
| 首次成功、重試與超時率 | 固定規則，保留全部失敗，不只計成功案例 |
| 誤接受率 | 接受字串與預先核對的標籤值比較；查得到資料不等於掃對 |
| 慢速尾端 | 除中位數外呈現分布與 P95，揭露偶發長等待 |

比較目前 MES 一維碼、候選改善版本與 QR；若舊 AppSheet 可合法使用，再納入舊流程。固定同台 iPad、版本、標籤、光線、距離與網路，交錯測試順序；另測反光、小字、彎曲與低光情境。更換碼制與更換引擎是不同因素，不混成單一改善量。

掃碼測試與紙本／MES 三類論文表單分開統計。沒有實測前不承諾一維碼一定與 QR 一樣快，也不填寫估計改善百分比。
